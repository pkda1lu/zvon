# Свой почтовый сервер для Zvon на той же VPS

Инструкция по настройке отправки писем (коды регистрации, входа и 2FA) с
собственного сервера на домене `zvonserver.ru`, без внешних почтовых сервисов.

Команды написаны для **Ubuntu 22.04/24.04 или Debian 12**. На других системах
отличаются пути и имена пакетов.

Схема: Zvon отправляет письма на Postfix по локальной сети (127.0.0.1), Postfix
подписывает их DKIM и отдаёт наружу. Входящая почта в базовом варианте не
настраивается — она нужна только для служебных адресов, см. раздел 8.

---

## 0. Проверьте это ДО начала работы

Два условия — блокирующие. Если хотя бы одно не выполняется, дальше идти
бессмысленно: почта не будет доставляться, и потрачено будет полдня.

### 0.1 Открыт ли исходящий порт 25

Большинство хостеров блокируют его по умолчанию для борьбы со спамом.

```bash
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/gmail-smtp-in.l.google.com/25' && echo "порт 25 открыт" || echo "порт 25 ЗАКРЫТ"
```

Если закрыт — напишите в поддержку хостинга с просьбой открыть. Обычно
открывают после короткого объяснения, зачем. **Обходных путей нет**: без порта 25
отправлять напрямую невозможно.

### 0.2 Можно ли поставить PTR-запись

PTR (обратный DNS) — это соответствие «IP → имя хоста». Почти все крупные
почтовые системы отклоняют письма от серверов без корректной PTR.

Смотрим текущую:

```bash
dig -x ВАШ_IP +short
```

Нужно, чтобы она была равна `mail.zvonserver.ru`. Ставится **только через панель
хостера или их поддержку** — в вашей DNS-зоне это сделать нельзя.

### 0.3 Проверьте, не в чёрных ли списках IP

```bash
dig +short ВАШ_IP_В_ОБРАТНОМ_ПОРЯДКЕ.zen.spamhaus.org
```

Пустой ответ — хорошо. Если что-то вернулось, IP в списке (бывает, что достался
«по наследству» от прежнего владельца) — нужно подавать заявку на делистинг.

## 1. DNS-записи

### 1.0 Сначала посмотрите, что в зоне уже есть

**Не пропускайте этот шаг.** Домен почти наверняка обслуживался хостером, и в
зоне уже лежат его почтовые записи. Слепое добавление новых ломает и старое, и
новое.

```bash
nslookup -type=MX  zvonserver.ru 8.8.8.8
nslookup -type=TXT zvonserver.ru 8.8.8.8
nslookup -type=TXT _dmarc.zvonserver.ru 8.8.8.8
```

Что вы можете увидеть и что с этим делать:

**Уже есть запись `v=spf1 ...`** — самое опасное. SPF-запись на домене должна
быть **ровно одна**: по RFC 7208 несколько записей дают `permerror`, и проверка
SPF перестаёт работать полностью — хуже, чем если бы её не было вовсе.
Существующую нужно **заменить**, а не добавить рядом.

Если прежний отправитель (хостер, рассыльщик, форма на сайте) должен продолжать
слать почту от домена — включите его через `include:`:

```
v=spf1 ip4:ВАШ_IP include:домен-прежнего-отправителя -all
```

Если нет — просто `v=spf1 ip4:ВАШ_IP -all`.

**Уже есть записи MX** — значит домен где-то принимает почту. Здесь стоит
остановиться и решить: нужен ли вам приём почты на своей VPS вообще.

Для Zvon — **не нужен**. MX отвечает только за приём, а приложение почту лишь
отправляет: коды регистрации, входа и 2FA уходят наружу, входящие ему не нужны.
Поэтому самый простой и безопасный путь — **не трогать MX совсем**, оставив
приём там, где он работает. Служебные адреса (`postmaster@`, `abuse@`, и адрес
для отчётов DMARC) заводятся обычными ящиками у прежнего почтового хостера, и
раздел 8 этой инструкции тогда не нужен.

Менять MX стоит, только если вы сознательно переносите на VPS и приём тоже.
Тогда старые записи нужно **удалить**, а не дополнить: при равном значении
Preference отправители выбирают сервер случайно, и почта будет приходить то
туда, то сюда.

### 1.1 Что добавить

| Тип | Имя | Значение | Обязательно |
|---|---|---|---|
| A | `mail` | `ВАШ_IP` | да |
| TXT | `@` | `v=spf1 ip4:ВАШ_IP -all` (см. 1.0 про замену) | да |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:dmarc@ваш-домен; fo=1` | да |
| MX | `@` | `10 mail.zvonserver.ru.` | только если переносите приём почты |

DKIM добавим позже, на шаге 5, когда сгенерируем ключ.

Про имена: `@` означает корень зоны — саму `zvonserver.ru`. В панелях эти записи
редактируются в зоне домена, а **не** в подзоне `mail`. DMARC живёт строго по
имени `_dmarc.<домен>`: если положить его в корень или в `mail`, он не найдётся.
В некоторых панелях для этого нужно создать отдельную подзону `_dmarc` — запись
A в ней не нужна, DMARC читается только из TXT.

Про точку в конце `mail.zvonserver.ru.` — она означает полное имя. Без неё
некоторые панели дописывают домен второй раз и получается
`mail.zvonserver.ru.zvonserver.ru`. Если панель точку не принимает — значит
подставляет домен сама; проверьте результат через `nslookup`.

Про SPF: `-all` означает «письма с других адресов считать поддельными». Режим
строгий и правильный, но убедитесь, что вы перечислили всех, кто отправляет от
имени домена.

Про DMARC: начинаем с `p=none` — режим наблюдения, письма не отклоняются, но вы
получаете отчёты. Через 2–4 недели, убедившись, что всё подписывается, меняйте
на `p=quarantine`, затем `p=reject`. Адрес в `rua=` должен реально принимать
почту, иначе отчёты потеряются.

### 1.2 Проверка

Через 10–15 минут после сохранения:

```bash
nslookup -type=TXT zvonserver.ru 8.8.8.8        # ровно одна строка v=spf1
nslookup -type=TXT _dmarc.zvonserver.ru 8.8.8.8 # v=DMARC1
nslookup mail.zvonserver.ru 8.8.8.8             # ваш IP
```

## 2. Имя хоста

```bash
sudo hostnamectl set-hostname mail.zvonserver.ru
```

Проверьте `/etc/hosts` — там должна быть строка:

```
127.0.1.1 mail.zvonserver.ru mail
```

## 3. TLS-сертификат — только если принимаете почту

**Если MX остался у прежнего хостера (вариант из 1.0) — пропустите этот раздел.**

Сертификат нужен параметрам `smtpd_tls_*`, а приставка `smtpd` означает приём
почты: он предъявляется чужим серверам, когда те подключаются к вам. При
`inet_interfaces = loopback-only` снаружи никто не подключается, и предъявлять
его некому.

Для отправки работает `smtp_tls_security_level = may` — там Postfix выступает
клиентом, собственный сертификат ему не нужен, шифрование с принимающей стороной
всё равно устанавливается.

Если приём почты всё-таки настраивается:

```bash
sudo apt update
sudo apt install -y certbot
sudo systemctl stop nginx        # если 80-й порт занят
sudo certbot certonly --standalone -d mail.zvonserver.ru
sudo systemctl start nginx
```

Вариант с `--webroot` подходит, только когда веб-сервер действительно отдаёт
файлы из указанного каталога по адресу `mail.zvonserver.ru`. Частая ошибка:
поддомен обслуживается тем же сервером, что и основной сайт, а тот отвечает 404
на `/.well-known/acme-challenge/...` — тогда проверка не проходит. Надёжнее
остановить веб-сервер на минуту и взять `--standalone`.

Сертификат появится в `/etc/letsencrypt/live/mail.zvonserver.ru/`.

## 4. Postfix

```bash
sudo apt install -y postfix
```

В мастере выбирайте **Internet Site**, system mail name — `zvonserver.ru`.

Далее правим конфигурацию:

```bash
sudo postconf -e "myhostname = mail.zvonserver.ru"
sudo postconf -e "mydomain = zvonserver.ru"
sudo postconf -e "myorigin = \$mydomain"

# Принимаем письма только с самой машины: наружу порт SMTP не смотрит,
# открытым релеем сервер не станет.
sudo postconf -e "inet_interfaces = loopback-only"
sudo postconf -e "mynetworks = 127.0.0.0/8 [::1]/128"

# Шифрование исходящих соединений, когда принимающая сторона его поддерживает.
sudo postconf -e "smtp_tls_security_level = may"
sudo postconf -e "smtp_tls_loglevel = 1"
sudo postconf -e "smtpd_tls_cert_file = /etc/letsencrypt/live/mail.zvonserver.ru/fullchain.pem"
sudo postconf -e "smtpd_tls_key_file = /etc/letsencrypt/live/mail.zvonserver.ru/privkey.pem"

# Ограничение размера письма — 10 МБ достаточно для кодов и уведомлений.
sudo postconf -e "message_size_limit = 10485760"

sudo systemctl restart postfix
```

`inet_interfaces = loopback-only` — важная строка. Она означает, что Postfix
слушает только localhost, и снаружи к нему подключиться нельзя. Именно поэтому
Zvon не нужны логин и пароль: доверие определяется тем, что процесс работает на
той же машине.

Проверка:

```bash
echo "Тест" | mail -s "Проверка" ваш_адрес@yandex.ru
sudo tail -f /var/log/mail.log
```

Если пакета `mail` нет: `sudo apt install -y mailutils`.

## 5. DKIM-подпись

Без DKIM письма почти гарантированно попадут в спам.

```bash
sudo apt install -y opendkim opendkim-tools
sudo mkdir -p /etc/opendkim/keys/zvonserver.ru
cd /etc/opendkim/keys/zvonserver.ru
sudo opendkim-genkey -s mail -d zvonserver.ru -b 2048
sudo chown -R opendkim:opendkim /etc/opendkim
sudo chmod 600 mail.private
```

Настройка `/etc/opendkim.conf` — добавьте или замените:

```
Domain                  zvonserver.ru
KeyFile                 /etc/opendkim/keys/zvonserver.ru/mail.private
Selector                mail
Mode                    sv
Canonicalization        relaxed/simple /
Socket                  inet:8891@localhost
UserID                  opendkim:opendkim
```

Связываем с Postfix:

```bash
sudo postconf -e "milter_default_action = accept"
sudo postconf -e "milter_protocol = 6"
sudo postconf -e "smtpd_milters = inet:localhost:8891"
sudo postconf -e "non_smtpd_milters = inet:localhost:8891"

sudo systemctl restart opendkim postfix
```

Теперь возьмите публичный ключ и добавьте его в DNS:

```bash
sudo cat /etc/opendkim/keys/zvonserver.ru/mail.txt
```

Запись:

| Тип | Имя | Значение |
|---|---|---|
| TXT | `mail._domainkey` | содержимое из `mail.txt` (склейте части в одну строку, без кавычек и скобок) |

Проверка через несколько минут:

```bash
dig +short mail._domainkey.zvonserver.ru TXT
```

## 6. Настройка Zvon

В `server/.env`:

```
SMTP_HOST=127.0.0.1
SMTP_PORT=25
SMTP_SECURE=false
MAIL_FROM=noreply@zvonserver.ru
```

`SMTP_USER` и `SMTP_PASS` **не нужны** — для локального релея код их не требует
(см. `server/utils/mail.js`, флаг `isLocalRelay`).

`MAIL_FROM` обязателен и должен быть на домене `zvonserver.ru`, иначе DKIM-подпись
не будет соответствовать отправителю и проверки не пройдут.

Перезапустите сервер. В логе должно появиться:

```
[mail] Соединение с 127.0.0.1 установлено, отправитель: noreply@zvonserver.ru
```

Если вместо этого ошибка подключения — Postfix не запущен или слушает не тот
интерфейс.

## 7. Проверка доставляемости

Это главный этап. Технически рабочая настройка ещё не значит, что письма дойдут.

**Тест 1 — оценка настроек.** Откройте https://www.mail-tester.com, скопируйте
выданный адрес и отправьте на него письмо через Zvon (например, запросите код
входа, временно поменяв себе почту). Нужен результат **9/10 или 10/10**. Всё
ниже 8 означает проблему, которую сервис вам назовёт.

**Тест 2 — заголовки у реальных получателей.** Отправьте себе на Яндекс, Mail.ru
и Gmail. Откройте исходный текст письма и найдите:

```
dkim=pass
spf=pass
dmarc=pass
```

Три `pass` — настройка верна.

**Тест 3 — попадание в папку.** Проверьте, что письмо во «Входящих», а не в
«Спаме», у всех трёх. Свежий домен могут первое время класть в спам даже при
правильных подписях — репутация набирается со временем.

## 8. Служебные адреса

**Этот раздел нужен только если вы переносите на VPS и приём почты тоже.**
Если MX остался у прежнего хостера (см. 1.0 — обычно так и надо), заведите
служебные адреса обычными ящиками в его панели и пропустите раздел.

По RFC 2142 домен должен принимать почту на `postmaster@` и `abuse@`. Плюс на
адрес из DMARC-записи будут приходить отчёты. Проще всего переслать всё на
существующий ящик:

```bash
echo "postmaster: ваш_личный@yandex.ru" | sudo tee -a /etc/aliases
echo "abuse: ваш_личный@yandex.ru" | sudo tee -a /etc/aliases
echo "dmarc: ваш_личный@yandex.ru" | sudo tee -a /etc/aliases
sudo newaliases
```

Для этого Postfix должен принимать входящую почту — тогда `inet_interfaces` из
раздела 4 меняется на `all`, и открывается порт 25 во внешнем файрволе. Если
принимать почту не хотите, укажите в DMARC-записи внешний адрес.

## 9. Что делать дальше

**Первую неделю** смотрите `/var/log/mail.log` на предмет отказов:

```bash
sudo grep -E "status=(bounced|deferred)" /var/log/mail.log | tail -30
```

**Раз в месяц** проверяйте чёрные списки — попадание туда происходит незаметно,
а письма начинают пропадать.

**Через 2–4 недели** ужесточите DMARC: `p=none` → `p=quarantine` → `p=reject`.

**Продлением сертификата** займётся certbot сам, но Postfix нужно перезапускать
после обновления:

```bash
echo 'systemctl reload postfix' | sudo tee /etc/letsencrypt/renewal-hooks/deploy/postfix.sh
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/postfix.sh
```

---

## 10. Если что-то не работает

| Симптом | Вероятная причина |
|---|---|
| `Connection refused` в логе Zvon | Postfix не запущен либо `inet_interfaces` не включает loopback |
| Письма уходят, но не приходят | закрыт порт 25 или нет PTR — проверьте раздел 0 |
| `dkim=fail` | домен в `MAIL_FROM` не совпадает с подписанным, либо запись в DNS ещё не разошлась |
| `spf=fail` | IP отправителя не указан в SPF-записи |
| Всё `pass`, но письма в спаме | репутация нового домена; помогает время и стабильный небольшой объём |
| `Relay access denied` | отправка идёт не с localhost, проверьте `mynetworks` |

## Про 152-ФЗ

Собственный почтовый сервер на VPS в РФ **снимает трансграничную передачу**
адресов электронной почты: письма больше не проходят через иностранные сервисы.
Отдельного обработчика в политику вписывать не нужно — вы обрабатываете данные
сами.

В [02-politika-obrabotki-pd.md](152-fz/02-politika-obrabotki-pd.md), раздел 7.2,
строку про сервис доставки электронной почты после перехода нужно убрать или
заменить на «обработка осуществляется Оператором самостоятельно».
