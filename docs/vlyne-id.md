# Vlyne ID — единый вход в экосистему

Аккаунт Zvon **и есть** Vlyne ID. Отдельного реестра пользователей нет и не
будет: любой второй список людей немедленно порождает задачу сводить его с
первым — в трёх проектах, вручную, навсегда.

Vlyne ID живёт на том же сервере, что и Zvon, и выдаёт другим проектам
экосистемы (Vlyne Client, Vlyne VPN, всё будущее) право действовать от имени
пользователя, не показывая им пароль.

Публичные страницы: **<https://vlyneid.zvonserver.ru>** — для обычного
пользователя, **/developers** — инструкция для сторонних сервисов,
**/account** — личный кабинет.

---

## Почему OAuth 2.1 / OpenID Connect, а не своя схема

Соблазн написать «свой простой токен» здесь особенно велик: всё в одних руках,
доменов три, разработчик один. Против этого три довода.

1. **Проверяющих сторон много, и они на разных языках.** Под стандарт готовые
   библиотеки есть для Node, Python, Swift, Kotlin. Под свой формат придётся
   писать и отлаживать реализацию заново в каждом проекте.
2. **Неочевидные места уже решены.** Перехват кода на редиректе (PKCE),
   подмена ответа (state), привязка id_token к попытке входа (nonce), кража
   долгого токена (ротация с обнаружением повтора) — это не паранойя, это
   ошибки, которые совершали все, кто писал своё.
3. **Цена стандарта здесь равна нулю.** Реализован ровно нужный объём:
   authorization code + PKCE, refresh с ротацией, discovery, JWKS. Ни неявного
   потока, ни паролей в обмене — того, что в OAuth 2.1 и запрещено.

## Как это устроено

```
  Приложение                Браузер                Vlyne ID (сервер Zvon)
      |                        |                            |
      |-- login() ------------>|                            |
      |                        |-- GET /oauth/authorize --->|  проверка client_id,
      |                        |                            |  redirect_uri, scope, PKCE
      |                        |<-- 302 /vlyne/authorize ---|
      |                        |                            |
      |                     [экран согласия]                |  повторный вход:
      |                        |-- POST .../decision ------>|  autoApprove, 0 нажатий
      |                        |<-- redirectTo (?code=…) ---|
      |<-- redirect_uri?code --|                            |
      |                                                     |
      |------ POST /oauth/token (code + code_verifier) ---->|  проверка PKCE
      |<----- access_token + id_token + refresh_token ------|
      |                                                     |
      |------ GET /oauth/jwks.json (один раз) ------------->|  дальше подпись
      |                                                     |  проверяется локально
```

**Экран согласия рисует клиент Zvon** (`/vlyne/authorize`), а не сервер. Так
вход выглядит частью Vlyne, а не служебной формой, и — главное — токен сессии
Zvon уже лежит в этом браузере: «войти в другое приложение» не требует вводить
пароль заново. В этом и состоит обещанное «одно нажатие», а при повторном
входе — ноль: согласие запомнено, страница сразу уводит обратно.

### Что чем является

| | |
|---|---|
| `sub` | идентификатор пользователя Zvon. Тот же, что бот знает как `zvonId`, и тот же, что в API Zvon. Специально: третьего идентификатора в экосистеме быть не должно |
| `access_token` | JWT, RS256, час жизни. Проверяется публичным ключом — без обращения к Vlyne ID |
| `id_token` | кто вошёл, для самого приложения. Не годится для доступа к API |
| `refresh_token` | непрозрачная строка, 60 дней, ротация при каждом использовании |

**Почему RS256, а не HS256 как у сессий Zvon.** Симметричный секрет, розданный
всем проверяющим, — это секрет, которым каждый из них может выпустить токен от
имени любого пользователя. Приватный ключ Vlyne ID не покидает VPS; остальные
берут публичный по `/oauth/jwks.json`.

## Права доступа

Определены в `server/utils/vlyneScopes.js`. Приложение не может выдумать себе
право на ходу: запрос с правом вне справочника или вне списка, разрешённого
при регистрации, отклоняется.

| Право | Что даёт |
|---|---|
| `openid` | `sub` — постоянный идентификатор аккаунта |
| `profile` | имя, аватар, баннер, описание |
| `email` | почта и признак подтверждения |
| `telegram` | привязка к Telegram: идентификатор и имя |
| `offline_access` | долгий вход (refresh-токен) |

**Список закрыт границей предметной области.** Vlyne ID отвечает за вход и за
данные самого аккаунта — имя, почту, привязки. Подписки, платежи и прочее
принадлежат своим сервисам, и права на них выдаёт тот, кто ими распоряжается.
Единый вход, который заодно раздаёт доступ к чужим предметным областям,
перестаёт быть входом и становится общей связкой ключей от всего: тогда любая
ошибка в нём стоит не «чужой сервис узнал ник», а «чужой сервис купил подписку
за ваши деньги».

## Эндпоинты

| Адрес | Назначение |
|---|---|
| `GET /.well-known/openid-configuration` | описание провайдера (оно же по `/.well-known/oauth-authorization-server`) |
| `GET /oauth/authorize` | начало входа |
| `POST /oauth/token` | `authorization_code` и `refresh_token` |
| `GET /oauth/userinfo` | данные о владельце токена |
| `GET /oauth/jwks.json` | публичный ключ подписи |
| `POST /oauth/revoke` | отзыв refresh-токена |
| `POST /oauth/introspect` | состояние токена (только для confidential-клиентов) |
| `GET /oauth/logout` | выход, инициированный приложением |
| `GET /api/vlyne-id/grants` | подключённые приложения (токен сессии Zvon) |
| `DELETE /api/vlyne-id/grants/:clientId` | отозвать доступ приложения |
| `… /api/vlyne-id/clients` | реестр приложений, только для админа |

### Три страницы, а не одна

| Адрес (на поддомене) | Для кого |
|---|---|
| `/` | Обычный человек, пришедший по ссылке «Подробнее» с экрана входа |
| `/developers` | Разработчик, подключающий вход к своему сервису |
| `/account` | Личный кабинет владельца аккаунта |

Разделение не косметическое. На главную попадают, нажав «Подробнее» на экране
входа в Zvon: у этого читателя нет вопроса про PKCE, ему надо понять, что стало
с его аккаунтом. Таблица эндпоинтов на первом экране такого человека отпугивает,
поэтому всё техническое вынесено на `/developers`, а ссылка туда стоит в подвале.

На основном домене те же страницы доступны как `/vlyneid`, `/vlyneid/developers`
и `/vlyneid/account` — удобно для ссылок из интерфейса Zvon.

Оформление главной повторяет лендинг Zvon (неоновый градиент, крупная
типографика, стеклянные карточки), а фон — тот же шейдер «краски в воде», что
на экране «Моей волны» в мини-приложении Яндекс.Музыки
(`client/src/components/VibeBackground.tsx`). Живой фон включён на главной и на
экране входа в кабинет; внутри самого кабинета его нет намеренно — там плотные
списки, и движение за текстом мешает читать.

### Личный кабинет

Отвечает на вопрос «кто и откуда пользуется моим аккаунтом»: идентификатор
Vlyne ID, учётная запись, история действий (`GET /api/vlyne-id/activity`),
устройства (`/api/sessions`), подключённые приложения (`/api/vlyne-id/grants`)
и выгрузка персональных данных (`/api/personal-data/export`).

Вход выполняется здесь заново: поддомен — отдельный origin, и токен сессии
Zvon с основного домена сюда не попадает. Это не недоработка, а то же правило,
которое защищает вкладки друг от друга; API при этом общий, nginx проксирует
`/api` на тот же сервер.

Из-за этого блок nginx для поддомена обязан проксировать **весь** сайт, а не
только страницы: кабинет ходит на `/api` собственного origin. В сборке зашит
`VITE_API_URL=https://zvonserver.ru` (`client/.env.production`), поэтому
`getApiUrl()` в `AuthContext` проверяет хост **до** этой переменной — иначе
запросы уходили бы на главный домен и упирались в CORS. На всякий случай
поддомен добавлен и в список разрешённых источников в `server.js`.

История берётся из общего журнала действий с жёстким фильтром по исполнителю.
Смысл не в отчётности: список входов рядом со списком устройств — самый
понятный способ заметить, что аккаунтом пользуется кто-то ещё.

## Установка

### 1. Переменные окружения

```env
VLYNE_ID_ISSUER=https://vlyneid.zvonserver.ru
VLYNE_ID_WEB_URL=https://zvonserver.ru
# ключ подписи: по умолчанию создаётся сам в server/data/vlyne-id/private.pem
# VLYNE_ID_KEY_FILE=/etc/vlyne/vlyne-id.pem
```

`VLYNE_ID_ISSUER` — **поддомен**, а не основной домен. Vlyne ID продаётся
сторонним сервисам как отдельный продукт, и в их настройках должен стоять его
адрес, а не адрес Zvon. Значение попадает в поле `iss` каждого токена и
сверяется проверяющими посимвольно: расхождение в схеме или завершающем слэше
делает недействительными **все** выданные токены разом. Поэтому определиться
нужно до выдачи первых токенов.

`VLYNE_ID_WEB_URL` — наоборот, основной домен: экран согласия человек видит
там, где уже вошёл в свой аккаунт Zvon.

### 2. Поддомен в nginx

Отдельного процесса не нужно: и `/oauth/*`, и сама страница отдаются тем же
приложением, что и Zvon, — нужен только ещё один server-блок.

Сначала проверьте, не ловит ли существующая конфигурация любое имя:

```bash
grep -R "server_name" /etc/nginx/sites-enabled/
```

Если там перечислены конкретные домены (а не `_`), поддомен сейчас никем не
обслуживается и блок обязателен. Заводим его **без TLS** — сертификат добавит
certbot, и тогда не придётся угадывать пути к файлам:

```bash
cat > /etc/nginx/sites-available/vlyneid << 'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name vlyneid.zvonserver.ru;

    location / {
        proxy_pass http://127.0.0.1:5000;
        # Host обязателен: по нему приложение отличает поддомен Vlyne ID от
        # основного домена и подставляет нужный заголовок вкладки.
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
```

Веб-сокетов здесь намеренно нет: на этом домене живёт только витрина и
эндпоинты OAuth, а реальное время — на основном домене.

```bash
ln -s /etc/nginx/sites-available/vlyneid /etc/nginx/sites-enabled/vlyneid
```

```bash
nginx -t && systemctl reload nginx
```

Дальше certbot сам перепишет блок под TLS и добавит редирект с 80-го порта.
DNS к этому моменту уже должен указывать на сервер, иначе проверка владения
доменом не пройдёт:

```bash
certbot --nginx -d vlyneid.zvonserver.ru
```

Проверка после настройки:

```bash
curl -s https://vlyneid.zvonserver.ru/.well-known/openid-configuration | head -5
curl -s https://vlyneid.zvonserver.ru/oauth/jwks.json
```

В первом ответе поле `issuer` должно совпадать с `VLYNE_ID_ISSUER` посимвольно —
расхождение обнаружится не здесь, а позже, отказом в чужом проекте.

### 3. Ключ подписи

При первом запуске генерируется RSA-2048 в `server/data/vlyne-id/private.pem`
с правами `600`. Каталог в `.gitignore`.

Смена ключа = мгновенный разлогин во всех проектах. Для эксплуатации это
значит: ключ надо включить в резервные копии сервера, иначе восстановление из
бэкапа без него обернётся тем же самым.

Проверить, что всё сошлось (обе команды работают без базы и без сети):

```bash
node server/scripts/vlyneSelfTest.js   # ключи, подпись, JWKS, права
node server/scripts/vlyneFlowTest.js   # весь поток входа целиком
```

### 4. Регистрация приложений

Два пути, и они не взаимозаменяемы.

**Свои приложения экосистемы** (Vlyne Client, VPN-бот) заводятся скриптом на
VPS — им не у кого просить разрешение, и модерировать себя самому бессмысленно.

**Сторонние сервисы** подают заявку в кабинете разработчика
(`/developers/cabinet`). Заявку читает модератор в Zvon: Настройки →
Модерация → вкладка «Vlyne ID». Он может одобрить, отклонить или задать
вопросы, не закрывая заявку.

Ключевое: **одобрение создаёт клиента само**, из тех же полей, которые
модератор только что прочитал. Руками в консоли ничего заводить не нужно — на
переносе полей ошибается именно человек, а решение остаётся за ним.

Что происходит при подаче и решении:

| Событие | Кто узнаёт | Как |
|---|---|---|
| Заявка подана | модераторы | событие в Zvon + системное уведомление тем, у кого он закрыт |
| Ответ разработчика | модераторы | так же |
| Вопросы от модератора | разработчик | письмо + уведомление + запись в кабинете |
| Одобрение или отказ | разработчик | письмо + уведомление + запись в кабинете |

Почта для разработчика важнее уведомления: на странице заявки никто не дежурит,
а решение может занять дни. Модераторам, наоборот, почта не нужна — очередь
они разбирают в Zvon.

**Секрет серверного приложения при одобрении не выдаётся.** Он нигде не
хранится в открытом виде, поэтому «показать ещё раз» невозможно — разработчик
выпускает его сам в кабинете, и старый при этом сразу перестаёт работать.

Ограничение: у одного человека не больше пяти открытых заявок. Это не
бюрократия, а защита очереди от десятка одинаковых черновиков.

### 4a. Свои приложения — скриптом

```bash
# Vlyne Client — десктоп/веб, секрета хранить негде
node server/scripts/vlyneClient.js create \
  --name "Vlyne Client" \
  --redirect "vlyne://auth/callback" \
  --redirect "https://client.vlyne.ru/auth/callback" \
  --scopes openid,profile,email,telegram,offline_access \
  --first-party

# Vlyne VPN — серверная часть, секрет хранить может
node server/scripts/vlyneClient.js create \
  --name "Vlyne VPN" --type confidential \
  --redirect "https://bot.vlyne.ru/oauth/callback" \
  --scopes openid,profile,telegram \
  --first-party
```

### 5. Что задаёт регистрация

Регистрация — это запись в коллекции `VlyneClient`, которая отвечает на один
вопрос: **что этому приложению вообще позволено просить**. Всё, что не описано
в ней, отклоняется ещё на `/oauth/authorize`, до того как пользователь что-то
увидит.

| Поле | Что задаёт | Почему это важно |
|---|---|---|
| `clientId` | публичное имя приложения в ссылке входа | не секрет, виден в адресной строке |
| `clientSecretHash` | sha256 секрета (только у confidential) | сам секрет не хранится нигде, как и пароль |
| `type` | `public` или `confidential` | определяет, обязан ли клиент доказывать себя секретом |
| `redirectUris` | точные адреса возврата | единственная защита от выдачи кода на чужой домен |
| `allowedScopes` | потолок прав | приложение не может попросить больше, даже подделав ссылку |
| `firstParty` | своё приложение экосистемы | согласие спрашивается один раз, а не при каждом входе |
| `allowRefreshTokens` | выдавать ли долгие токены | выключается для приложений, которым не нужен долгий вход |
| `accessTokenTtlSec` / `refreshTokenTtlSec` | сроки жизни токенов | по умолчанию час и 60 дней |
| `isActive` | выключатель | отключает вход мгновенно, не удаляя историю |

**`public` или `confidential`** — вопрос не о доверии, а о том, где выполняется
код. Браузерное приложение, десктоп, мобильное — `public`: секрет там хранить
негде, потому что весь код лежит у пользователя и легко читается. Серверная
часть — `confidential`: она может хранить секрет и обязана предъявлять его на
`/oauth/token`. PKCE обязателен обоим: он закрывает другую дыру — перехват кода
на редиректе, а не кражу секрета.

**`redirectUris` сверяется посимвольно.** Ни префиксов, ни шаблонов, ни
«поддомены тоже подойдут». Послабление здесь превращает Vlyne ID в открытый
перенаправитель: достаточно подставить свой адрес, попадающий под шаблон, и код
авторизации уедет чужому серверу. Поэтому все адреса — рабочие, отладочные,
кастомные схемы вроде `vlyne://auth/callback` — перечисляются заранее.

**`allowedScopes` — именно потолок, а не список по умолчанию.** Приложение в
каждом запросе само указывает, что просит; регистрация лишь ограничивает
сверху. Запрос с правом вне списка получает `invalid_scope` и до экрана
согласия не доходит.

**`firstParty`** избавляет свои приложения от бессмысленного ритуала: спрашивать
у человека разрешение на доступ Vlyne Client к Vlyne ID при каждом запуске —
это не защита, а привычка нажимать «Да» не читая. Побочное следствие: своим
приложениям refresh-токен выдаётся без явного `offline_access`.

### 6. Секрет приложения

Секрет показывается **один раз** — при создании или перевыпуске. В базе лежит
только его sha256, поэтому «посмотреть секрет ещё раз» невозможно by design:
утечка базы не даёт возможности выдать себя за приложение. Сравнение при
проверке идёт за постоянное время, чтобы по скорости ответа нельзя было
подобрать секрет посимвольно.

Потеряли — перевыпускайте, старый перестаёт работать сразу:

```bash
node server/scripts/vlyneClient.js secret vlyne_xxxxxxxxxxxx
```

### 7. Управление приложениями

```bash
node server/scripts/vlyneClient.js list                    # все приложения
node server/scripts/vlyneClient.js disable vlyne_xxx       # выключить вход
node server/scripts/vlyneClient.js enable  vlyne_xxx
node server/scripts/vlyneClient.js delete  vlyne_xxx       # удалить насовсем
node server/scripts/vlyneClient.js help
```

`disable` — обратимый выключатель: новые входы отбиваются, записи о согласиях
остаются. `delete` удаляет приложение **вместе** с выданными согласиями и
долгими токенами: иначе в «Подключённых приложениях» у людей остались бы
записи, не привязанные ни к чему.

То же самое доступно по HTTP для пользователя с ролью `admin` — это нужно,
когда до консоли VPS не дотянуться:

```
GET    /api/vlyne-id/clients
POST   /api/vlyne-id/clients
PATCH  /api/vlyne-id/clients/:clientId
POST   /api/vlyne-id/clients/:clientId/secret
DELETE /api/vlyne-id/clients/:clientId
```

Поля те же, что у скрипта; секрет так же возвращается один раз, в ответе на
создание или перевыпуск.

## Подключение проекта

### Клиент (браузер, Electron, SPA)

`sdk/vlyne-id/browser.js` — без зависимостей, копируется в проект.

```js
import { VlyneID } from './vlyne-id/browser.js';

const id = new VlyneID({
  issuer: 'https://vlyneid.zvonserver.ru',
  clientId: 'vlyne_xxx',
  redirectUri: window.location.origin + '/auth/callback',
  scopes: ['openid', 'profile', 'email', 'offline_access']
});

// страница /auth/callback
if (VlyneID.isCallback()) await id.handleCallback();

// где угодно
if (!id.isAuthenticated()) await id.login();

const user = id.user();                       // из id_token, без сети
const res  = await id.fetch('/api/что-то');   // токен подставится и обновится сам
```

### Ресурс на Node

`sdk/vlyne-id/node.js` — проверка подписи, без зависимостей.

```js
const { VlyneVerifier } = require('./vlyne-id/node');
const verifier = new VlyneVerifier({ issuer: 'https://vlyneid.zvonserver.ru', audience: 'vlyne_xxx' });

app.get('/api/profile', verifier.middleware({ scopes: ['profile'] }), (req, res) => {
  // req.vlyne = { sub, clientId, scopes, claims }
});
```

Внутри самого Zvon то же самое делает `server/middleware/vlyneAuth.js` —
`requireVlyneToken({ scopes: [...] })`, дополнительно подгружающий `req.user`.

### Ресурс на Python (телеграм-бот)

`sdk/vlyne-id/python/vlyne_id.py`.

```python
from vlyne_id import VlyneVerifier, VlyneTokenError

verifier = VlyneVerifier("https://vlyneid.zvonserver.ru", audience="vlyne_xxx")

try:
    claims = verifier.verify(token, require_scopes=["profile"])
except VlyneTokenError as e:
    return {"ok": False, "error": str(e)}

zvon_id = claims["sub"]   # ровно то, что бот уже хранит как zvonId
```

## Что это меняет для существующей связки с ботом

Сейчас Zvon ходит в бота по общему секрету `X-Zvon-Key`, называя пользователя
полем `zvonId` (`server/utils/vlyneBot.js`). Схема рабочая, но у неё два
свойства, которые мешают расти:

- **Доверие устроено «всё или ничего».** Обладатель `ZVON_API_KEY` может
  назваться любым `zvonId`. Реестр привязок на стороне бота это частично
  сдерживает, но проверить, что запрос действительно исходит от конкретного
  пользователя, нельзя.
- **Третий проект придётся подключать тем же способом** — ещё один общий
  секрет, ещё одна пара «кто кому доверяет».

С Vlyne ID запрос несёт токен **самого пользователя**, подписанный ключом,
который у бота есть только в публичной половине. `sub` при этом совпадает с
нынешним `zvonId`, то есть переход не требует миграции данных.

Важно, чем этот переход НЕ является: Vlyne ID не начинает распоряжаться
VPN-подпиской. Он отвечает ровно на вопрос «кто пришёл» — что этому человеку
можно делать с подпиской, по-прежнему решает бот, у которого она и живёт.
Прав вида `vpn:*` в справочнике нет намеренно.

### Что уже сделано

**Привязка переведена на Vlyne ID.** В мини-аппе бота есть кнопка «Войти через
Vlyne ID»: человек входит в свой аккаунт, бот получает подписанный токен и
связывает `sub` с его телеграмом. Шестизначный код больше не нужен — ни в боте,
ни в магазине Zvon.

Ключ связи не изменился: `sub` из токена — это тот же идентификатор, что раньше
приходил полем `zvonId`. Поэтому `zvon_links.json` не мигрировали, а магазин в
Zvon подхватывает привязку сам, тем же запросом `/api/zvon/status`.

Со стороны Zvon добавилось одно: при виде привязки заполняется локальная копия
`user.telegram`. Без неё право `telegram` в Vlyne ID отдавало бы `null` у
реально привязанного аккаунта — связь ведь создаётся на стороне бота, и Zvon
узнаёт о ней только из ответа на проверку статуса.

Файлы бота: `vlyne_id.py` (OAuth-клиент), `miniapp.py` (`/api/vlyneid/*` и
`/vlyneid/callback`), `zvon_link.py` (`link_direct`), `webapp/index.html`
(кнопка).

### Что осталось от старого пути

Обмен кодом (`/api/zvon/link` в боте, `POST /api/store/vpn/link` в Zvon,
команда `/link`) ещё жив, но интерфейсом не используется. Он держится только
ради тех, у кого открыт старый клиент; когда такие обращения пропадут из логов,
удаляются целиком — вместе с `claim()` в `zvon_link.py`.

Общий секрет `ZVON_API_KEY` при этом остаётся нужным: им подписаны обращения
Zvon к боту за состоянием подписки (`/api/state`, `/api/buy`). Vlyne ID отвечает
за то, кто пришёл, а не за то, что ему можно делать с подпиской, — эта граница
описана выше в разделе про права.

## Принятые решения и их цена

- **Согласие запоминается** — иначе «вход одним нажатием» им не является.
  Цена: список выданных доступов надо где-то показывать и уметь отзывать;
  это сделано в настройках, и отзыв немедленно гасит долгие токены.
- **PKCE обязателен всем, включая серверные приложения.** Он защищает не от
  кражи секрета, а от перехвата кода на редиректе — это разные угрозы.
- **Повторный обмен кода гасит выданные по нему токены.** Второй обмен либо
  гонка клиента, либо кража; различить их нельзя, поэтому выбран громкий
  отказ вместо тихого параллельного доступа.
- **Ключ генерируется сам при первом запуске.** Удобно, но обязывает:
  не потерять его при переустановке и включить в бэкап.
- **Заявку читает человек, но клиента создаёт машина.** Самообслуживания нет:
  список тех, кто может просить доступ к аккаунтам, должен быть проверяемым
  глазами. Зато всё вокруг решения автоматизировано — модератор отвечает за
  «да» или «нет», а не за аккуратность копирования полей.
- **Адреса возврата, права и тип у одобренного приложения не редактируются.**
  Их проверял модератор, и тихая правка обошла бы проверку. Зато есть выход:
  разработчик удаляет приложение в кабинете и подаёт заявку заново. Название,
  описание и ссылки править можно — они ни на что не влияют.
- **Одобрение обратимо.** Модератор может отозвать доступ (обратимо, с
  причиной, гасит выданные токены), вернуть его или удалить приложение
  насовсем. Решение, которое нельзя отменить, — это не решение, а ставка:
  приложение может начать вести себя не так, как обещало в заявке.
